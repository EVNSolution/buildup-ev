# buildup-ev 개발 · Git 워크플로우 가이드 (비개발자용)

> 목적: DB 구축 → 백엔드 → 프론트 → 앱 개발을 GitHub로 꾸준히 관리하는 방법을, 개발 경험이 적어도 따라할 수 있게 정리.
> 전제: 개발은 **Claude Code**(맥 터미널)에서, 배포는 별도 담당. git 명령은 대부분 Claude Code에게 시키면 됨.

---

## 0. 한 장 요약
- 저장소는 **하나(모노레포)** — DB/백엔드/프론트/앱/문서를 폴더로 분리
- **엑셀은 입력용, git엔 CSV/SQL로** 올린다 (엑셀은 변경추적 안 됨)
- 기능마다 **브랜치** 따서 개발 → 커밋 → 푸시 → PR → main 병합
- 프론트·앱은 백엔드와 **API로 통신**(직접 붙는 게 아님)
- 추천 순서: **DB 구축 → 백엔드(API) → 프론트 → 앱**

---

## 1. 저장소 구조 (모노레포)
하나의 GitHub repo에 폴더로 분리:
```
buildup-ev/
├─ docs/              # 기획서·DB스키마·장표 (지금 만든 산출물)
├─ db/
│  ├─ schema/         # 테이블 정의 (SQL 마이그레이션)
│  ├─ seed/           # 엑셀에서 변환한 실데이터 (CSV)
│  └─ templates/      # 담당자 배포용 엑셀 (참고)
├─ backend/           # API 서버
│  ├─ options/  quote/  cost/  loadcalc/  orders/  documents/  admin/
├─ frontend/          # 웹 (영업/특장사/관리자 3-Surface)
├─ app/               # 모바일 앱 (필요 시)
├─ shared/            # 공통 타입·API 계약 (선택)
├─ .gitignore
└─ README.md
```
- **왜 모노레포?** 작은 팀·1인 개발에선 저장소 하나가 제일 단순(한 번 clone, 한 곳에서 관리, Claude Code가 전체 맥락을 봄).
- 나중에 규모 커지면 분리(멀티레포)도 가능하지만 지금은 불필요.

## 2. DB: 엑셀 → Git
### 원칙
- **엑셀(.xlsx)은 바이너리** → git에서 변경내역(diff)이 안 보이고 충돌나기 쉬움.
- 그래서 git의 "진짜 데이터"는 **CSV(텍스트)** 또는 **SQL**로 둔다.

### 흐름
1. 담당자가 `buildup-ev_DB구축템플릿.xlsx` 채움
2. 채운 엑셀을 `db/templates/`에 커밋 (사람 참고용)
3. **변환 스크립트**로 각 시트 → `db/seed/{시트명}.csv` 생성 후 커밋 (← 변경추적 가능)
4. 테이블 구조는 `db/schema/001_init.sql` 등에 SQL로
5. 앱/DB 셋업 시 schema 적용 → seed CSV 적재

### Claude Code에게 시키는 예
> "db/templates의 엑셀을 읽어서 시트별로 db/seed에 CSV로 변환하는 스크립트 만들어줘. 그리고 실행해서 CSV 커밋해줘."

- 데이터 갱신될 때마다: 엑셀 교체 → 스크립트 재실행 → CSV 갱신 → 커밋/푸시.

## 3. 브랜치(작업트리) 워크플로우
### 개념
- `main` = **항상 돌아가는** 안정 버전 (여기서 직접 작업 X)
- `feature/...` = 기능 개발용 임시 가지
```
main ──●────────●─────────●  (안정)
        \        /         /
         ●──●──●  (feature/quote-engine)
```

### 한 사이클 (기능 1개)
1. 새 브랜치: `git checkout -b feature/quote-engine`
2. 개발 + **작게 자주 커밋**: `git add . && git commit -m "견적 공급가 계산 추가"`
3. 푸시: `git push -u origin feature/quote-engine`
4. GitHub에서 **PR(Pull Request)** 열어 검토
5. 이상 없으면 **main에 병합(merge)** → 브랜치 삭제

### Claude Code에게 시키는 예
> "견적 엔진 작업할 브랜치 feature/quote-engine 만들고 시작하자"
> "여기까지 커밋하고 푸시해줘. 커밋 메시지는 적절히."
> "main에 머지하고 브랜치 정리해줘"

- 백엔드 모듈은 폴더로 나누고(`backend/quote`), 개발 격리는 **브랜치**로.
- (고급: `git worktree`로 여러 브랜치 동시 작업도 가능하지만, 처음엔 브랜치만으로 충분.)

---

## 4. 프론트 / 앱을 백엔드와 "붙이기" = API
- 백엔드·프론트·앱은 **한 몸이 아님**. 백엔드가 **API(주소)**를 열고, 프론트·앱이 그걸 **호출**.
```
[프론트 웹] ─┐
             ├─→ (HTTP API) ─→ [백엔드] ─→ [DB]
[모바일 앱] ─┘
```
- 예: 백엔드가 `POST /api/quote` 제공 → 옵션 JSON 보내면 견적 JSON 반환. 프론트·앱은 같은 주소를 호출해 화면에 표시.
- **API 계약**(주소·입력·출력)을 먼저 정하면 백/프론트/앱을 **동시에** 개발 가능. (계약은 `shared/` 또는 docs에 문서화)
- "통합"이란 = 프론트·앱이 **같은 백엔드 API를 바라보게** 하는 것. 코드가 분리돼 있어도 API로 연결됨.

---

## 5. 추천 개발 순서
1. **DB 구축** — 엑셀 채움 → CSV/스키마 → 저장소 반영 (지금 단계)
2. **백엔드(API)** — DB 위에서 모듈별 API. 핵심부터: 옵션조회 → 견적 → 하중계산 → 주문/서류
3. **프론트** — 백엔드 API 호출해 영업 Surface부터 (Phase 1)
4. **앱** — 필요 시, 같은 API 재사용

이유: 위가 아래의 토대. DB·API가 있어야 프론트가 보여줄 게 생김.

## 6. 처음에 한 번 세팅
- repo 생성 후 clone (Claude Code에게: "이 repo clone 하고 위 폴더 구조 잡아줘")
- **`.gitignore`** 필수: `node_modules/`, `.env`, 빌드 산출물(`dist/`,`build/`), `.DS_Store`
- **`.env`(비밀번호·API키)는 절대 커밋 금지** → 대신 `.env.example`(빈 양식)만 커밋
- `README.md`에 "이게 뭐고 어떻게 돌리는지" 적기

---

## 7. 안 할 것 / 주의
- 비밀키·토큰·비밀번호를 코드/커밋에 넣지 않기 (`.env`로 분리, git 제외)
- `main`에서 직접 큰 작업 X → 항상 브랜치
- 거대한 커밋 X → 작게 자주 (되돌리기·검토 쉬움)
- 엑셀 원본을 "데이터 소스"로 앱에 직접 물리지 않기 → CSV/DB로
