## 1. 지금 당장 챙길 것 ★ (앱보다 먼저)

앱은 후순위지만, **지금 웹 작업에서 어기면 나중에 되돌리기 비싼 것들**이 있다.
아래는 앱 착수 전까지 웹 개편을 하면서 지켜야 한다.

### 1-1. 계산 로직은 `shared/` 에만 둔다 ★★
- 가격·보조금·세율·하중 계산은 **`shared/` TypeScript 패키지 한 곳에만** 존재한다.
- 프론트 컴포넌트 안에서 금액을 다시 계산하지 않는다. 화면은 결과를 표시만 한다.
- **이유**: 최근 부가세 환급 기준이 바뀌어 코드·엑셀·저장된 견적을 전부 다시 맞춘 적이 있다.
  계산이 두 벌이면 이런 변경마다 값이 갈린다. 앱이 생기면 세 벌이 된다.
- 이 원칙을 지키면 앱 형태 선택이 자유로워지고, 안 지키면 RN·하이브리드 외엔 선택지가 없어진다.

### 1-2. 화면 설계는 태블릿 기준으로
- UI 개편 6단계(태블릿 대응)를 제대로 해두면 **앱 화면을 다시 설계하지 않아도 된다.**
- 앱도 **태블릿 가로가 1순위**, 휴대폰은 조회 중심. 웹과 같다.
- 앱이라고 화면을 새로 정의하지 말 것.

### 1-3. 서버가 최종 금액의 기준
- 화면에 표시하는 금액은 참고, **저장·발송되는 최종 금액은 서버 계산값**을 쓴다.
- 앱 버전이 뒤처져도 잘못된 금액이 나가지 않게 하는 유일한 방법이다.

### 1-4. 정책·문구는 서버에서 내려받기
- 앱은 스토어 심사 때문에 즉시 수정이 안 된다.
- **가격 규칙·안내 문구·정책 텍스트를 앱에 하드코딩하지 않는다.**
- 웹 개편 단계에서도 이런 값은 DB/설정에서 오게 해두면 앱 전환이 쉬워진다.

## 2. 앱 형태 — 착수 시 결정 (판단 기준)

**최우선 제약: 계산 로직을 한 벌로 유지할 수 있는가.**

| 형태 | 계산 한 벌 유지 | 인증 재작업 | 배포 속도 | 네이티브 기능 | 개발량 |
|---|---|---|---|---|---|
| **React Native** | ○ `shared/` 그대로 공유 | 필요 (Bearer+CORS) | 스토어 심사 | 푸시·카메라·생체 모두 | 중 |
| **웹뷰 하이브리드** | ◎ 자동 (같은 코드) | 필요 | 스토어 심사(껍데기만) | 푸시·카메라 브리지 | 소 |
| **PWA** | ◎ 자동 (같은 코드) | **불필요** (쿠키 유지) | **웹과 동일 즉시** | 푸시(iOS 제한)·카메라·WebAuthn | 최소 |
| **네이티브** | ✕ 언어별 재구현 → 값 갈림 위험 | 필요 | 스토어 심사 | 전부 | 대 (2배) |

**권장 순서**: 웹뷰 하이브리드 또는 RN. 네이티브는 계산 이중화 위험 때문에 권하지 않는다.
네이티브를 택한다면 **계산을 어떻게 한 벌로 유지할지 답을 먼저 정해야 한다**
(예: 모든 금액을 서버 API로만 받고 클라이언트 계산 0).

**PWA 참고**: 인증 재작업·스토어 심사가 없어 가장 싸다. 다만 iOS는 홈 화면 추가 시에만
푸시가 되고 백그라운드 처리가 제한적이다. 갤럭시탭(안드로이드) 위주라면 실용적 선택지.
착수 시점에 "네이티브가 꼭 필요한 이유"가 명확하지 않으면 PWA를 먼저 검토할 것.

## 3. 선결 과제 — 인증 (화면보다 먼저)

**지금 구조로는 네이티브 앱이 로그인할 수 없다.**

- 현재: JWT를 `access_token` **httpOnly 쿠키**로만 읽음, `sameSite: strict`, **CORS 설정 없음**
- 같은 도메인에서 서빙되는 웹은 문제없지만, 앱은 이 방식으로 인증 불가

**필요 작업 (앱 1단계 = 화면이 아니라 이것)**
1. **Bearer 토큰 인증** 추가 (기존 쿠키 방식과 병행 — 웹은 그대로 유지)
2. **CORS 허용** (앱 오리진 화이트리스트)
3. **토큰 갱신(리프레시)** — 만료 시 재로그인 없이 갱신
4. **PDF 접근**: 견적서·계약서·서명본은 전부 인증 필요한 API 응답이다.
   URL만 외부 브라우저로 열면 안 열린다. **앱이 인증 헤더를 붙여 받아 자체 뷰어로 표시**하는 흐름 필요

※ PWA로 가면 1~3은 불필요(쿠키 그대로), 4도 불필요(브라우저가 처리).

## 4. 앱의 존재 이유 (이게 없으면 홈 화면 바로가기와 다르지 않다)

### 4-1. 푸시 알림 ★ 1순위
현재 서버에 **푸시 인프라가 전혀 없다.** 새로 붙여야 한다.

| 대상 | 알림 | 시점 |
|---|---|---|
| **영업** | 서명 완료 | 고객이 전자서명을 마쳤을 때 (모두싸인 webhook 수신 시) |
| **관리자** | 승인 대기 | 주문 검증·승인이 필요한 건이 생겼을 때 |
| **특장사** | 작업 배정 | 새 주문이 배정되거나 단계가 바뀌었을 때 |

**빈도 조절 원칙** — 알림이 잦으면 사용자가 바로 꺼버린다.
- 위 3종으로 시작하고 그 이상 늘리지 않는다
- 상태 변경 전부를 알리지 않는다 (제작 진행 단계마다 알림 ✕)
- 사용자별 on/off 설정 제공
- 같은 건에 대한 중복 알림 억제

### 4-2. 카메라
- 사업자등록증·화물운송사업허가증 촬영 첨부
- **현재 서류 첨부 기능은 보류 상태** → 앱과 함께 설계하면 자연스럽다

### 4-3. 생체 인증 로그인
- 현장에서 매번 비밀번호를 치지 않게

### 4-4. 오프라인 / 약한 네트워크
- 옵션·보조금 등 **기준데이터를 미리 받아두고**, 통신이 끊겨도 옵션 선택·금액 확인까지 가능
- **견적 저장·발송은 온라인에서만** (오프라인 저장 후 동기화는 값 충돌 위험 → 하지 않음)

## 5. 웹과의 관계 — 앱은 전체 대체가 아니다

| 화면 | 앱 포함 여부 | 이유 |
|---|---|---|
| **영업 — 컨피규레이터** | ○ | 현장 상담의 핵심 |
| **영업 — 견적·주문 목록** | ○ | 상태 확인·발송 |
| **영업 — 마이페이지** | ○ | 조회 |
| **관리자** | △ 조회만 | 승인 알림 받고 확인하는 정도. 기준정보 관리(옵션DB·계정)는 PC에서 |
| **특장사** | △ 조회·단계이동 | 작업 배정 확인과 단계 이동만. 상세 관리는 PC |

**원칙**: 앱은 **현장에서 필요한 것**만. 데이터 입력이 많거나 표가 큰 화면(옵션DB·계정관리)은
PC에 둔다. 전 기능 이식은 비용 대비 효과가 낮다.

---

## 6. 사용 맥락 (웹과 동일 — 새로 정의하지 않는다)

- 주 사용자 **영업**, 주 상황 **고객 앞 태블릿 가로**
- **화면을 고객이 함께 본다** → 다른 고객 정보·실적 노출 금지 (웹과 같은 원칙)
- **고객이 서명하는 화면은 우리 앱이 아니다** — 카카오 알림톡/메일로 전자서명 업체 화면이 열린다.
  고객용 앱을 설계할 필요 없음
- **3D는 외부(VIVAR) 임베드** → 앱에서도 웹뷰. **16:9 유지**
- **권한 14개 모듈**로 화면이 바뀌는 규칙 동일 (권한 없으면 **숨김**)

## 7. 단계

| 단계 | 내용 | 비고 |
|---|---|---|
| **A** | 인증 기반 (Bearer + CORS + 리프레시) | 화면 아님. PWA면 생략 |
| **B** | 푸시 인프라 (서버측 + 토큰 관리 + 발송 규칙) | 앱의 존재 이유 1순위 |
| **C** | 앱 껍데기 + 로그인 + 영업 화면 (컨피규레이터·목록) | 태블릿 가로 1순위 |
| **D** | 카메라 첨부 (서류 첨부 기능과 함께 설계) | |
| **E** | 생체 인증 | |
| **F** | 오프라인 기준데이터 캐시 | 저장·발송은 온라인 전용 |
| **G** | 관리자·특장사 조회 화면 | 필요성 재판단 후 |

## 8. 착수 전 확정할 것

- **앱 형태** (§2 기준으로 판단) — 네이티브 선택 시 계산 한 벌 유지 방법을 먼저 답할 것
- **iOS/Android 둘 다인가** — 갤럭시탭 먼저 도입 예정이므로 Android 우선 가능
- **사내 배포인가 스토어 공개인가** / Apple Developer · Google Play 계정 보유 여부
- **영업팀 실제 기기 구성** (도입 후 확정)
- 최소 지원 OS 버전

---

## 9. 하지 않는 것

- 고객용 앱 (서명은 전자서명 업체 화면)
- 앱에서 가격·보조금 재계산
- 오프라인 견적 저장·발송
- 옵션DB·계정관리 등 대형 표 화면의 앱 이식
- 앱 전용 UX 재정의 (웹과 같은 맥락·같은 원칙)
