# 모두싸인 전자계약 연동 — 설계(뼈대)

> 대상: **구매계약서** 1종. 서명자 = **고객 1인**. 방식 = **B(우리가 계약서 PDF 자동생성 후 업로드)**.
> 계약서 양식 미확정 상태에서 **연동 뼈대를 먼저 구축**하고, 양식이 오면 생성기만 교체한다.
> 관련: docgen 파이프라인(서류자동생성), CLAUDE.md 배포·보안 규칙 준수.

---

## 0. 지금 만들 수 있는 것 vs 양식 대기

| 지금 구축 (양식 무관) | 양식 확정 후 |
|---|---|
| 계약 상태 모델·테이블 | 실제 계약서 레이아웃/문구 |
| 모두싸인 API 클라이언트(발송·조회·다운로드) | anchor 텍스트 최종 확정 |
| webhook 수신·멱등·상태갱신 | 요청자입력 필드 좌표/anchor 매핑 |
| 서명본 저장 | 법무 검토 반영 |
| 발송 UI(수단 선택·상태 뱃지) | |
| **placeholder 계약서 PDF**로 E2E 테스트 | placeholder → 실양식 교체(1곳) |

→ 양식은 **1개 함수(계약서 PDF 생성기)** 뒤에 격리한다. 나머지는 전부 지금 개발 가능.

## 1. 계약서 생성기 ↔ 발송기 인터페이스 (이걸 먼저 고정)

```ts
// 계약서 PDF 생성 — 양식이 바뀌어도 이 시그니처는 유지
interface ContractInput {
  order_id: string;
  customer: { name: string; email?: string; phone?: string; biz_no?: string };
  vehicle:  { model: string; options: string[]; };
  price:    { supply: number; vat: number; total: number; /* 필요시 확장 */ };
  terms:    Record<string, string | number>;   // 납기·특약 등 가변
}
// 반환: 서명 필드를 anchor로 잡을 수 있는 텍스트 PDF(폰트 임베딩 필수)
function generateContractPdf(input: ContractInput): Buffer;
```

**Anchor 텍스트 규약(양식과 무관하게 미리 약속)** — 실제 양식에 이 텍스트만 포함시키면 됨:
| anchor 텍스트 | 필드 | 타입 |
|---|---|---|
| `[고객서명]` | 고객 서명란 | SIGNATURE |
| `[서명일자]` | 서명일 | SIGNING_DATE(좌표) |
| `[고객성명]` | 성명 확인 | TEXT |

placeholder 양식엔 이 텍스트들만 있으면 개발·테스트 가능. 실양식 교체 시 동일 텍스트 유지.

## 2. 모두싸인 API 연동 (백엔드, 서버 전용)

- 인증: `MODUSIGN_API_KEY` = base64(`이메일:API-KEY`) → `Authorization: Basic ...`.
  **`.env`/시크릿에만. 프론트 노출·커밋 절대 금지.** 서버 .env는 배포담당이 주입.
- 발송: `POST /documents` — PDF(base64) + `participants[0]` = 고객.
  - `signingMethod.type` = **EMAIL | KAKAO** (발송 화면에서 선택, value=주문에 저장된 고객 email/phone)
  - `fields` = §1 anchor 규약으로 배치
- 조회: 문서 상태·서명본 다운로드 API (완료 시)
- ⚠️ 요청 본문 **UTF-8** 필수. 서명필드 ≤100 / 전체필드 ≤2000.

## 3. 계약 상태 모델

새 테이블 `purchase_contract` (스키마 변경 전 pg_dump 백업):
```
purchase_contract(
  id, order_id, modusign_document_id,
  signing_method,           -- EMAIL | KAKAO
  status,                   -- 아래 enum
  customer_snapshot(jsonb), -- 발송시점 고객 이름/연락처 스냅샷
  signed_pdf_path,          -- 완료 서명본 저장 경로(DOC_STORAGE_DIR 하위, 워크트리 밖)
  sent_at, completed_at, created_at, updated_at
)
```
상태 enum: `DRAFT → SENT → VIEWED → SIGNING → COMPLETED` / 분기 `REJECTED`, `CANCELED`.

## 4. Webhook 처리

- 엔드포인트: `POST /api/v1/webhooks/modusign`
- **즉시 2xx 응답 후 내부처리**(10초 내 응답, 아니면 최대 5회 재전송).
- **멱등**: `webhook_event(document_id, event_type, received_at)` dedup — 중복 수신 무시.
- 이벤트 매핑: document_started→SENT, 서명입력→SIGNING, 모든완료→COMPLETED(+서명본 다운로드·저장), 거절→REJECTED, 취소→CANCELED.
- ⚠️ **위조 방지 확인 필요**: 모두싸인 webhook 서명검증(secret) 유무 미확인.
  없으면 방어로직 — 이벤트 수신 시 `document_id`를 API로 재조회해 상태 검증 후 반영.

## 5. 화면 (RBAC)

- 주문 상세에 **계약 탭**: 발송 버튼(서명수단 라디오 EMAIL/KAKAO만 선택, 고객정보는 이미 주문에 있음) → 상태 뱃지(발송/서명중/완료/거절/취소) → 완료 시 서명본 다운로드.
- 발송·조회 = 영업/관리자. 서명 = 고객(모두싸인 링크). 영업 화면에 API KEY 노출 금지.

## 6. 비용·정책

- 서명요청은 **건당 과금**(채널 무관). **주문 확정 시 1회만 발송**. 견적 단계 발송 금지.
- 재발송/취소 정책: 거절·취소 시 재발송 허용, 이력은 purchase_contract에 누적.

## 7. 개발·검증 순서

1. `purchase_contract` 테이블 + 상태 enum (백업 후)
2. 모두싸인 클라이언트(발송·조회·다운로드) — API KEY는 env
3. webhook 수신·멱등·상태갱신·서명본 저장
4. `generateContractPdf` **placeholder**(§1 anchor 텍스트 포함 최소 PDF)로 E2E:
   발송 → (테스트 서명) → webhook 완료 → 서명본 저장 확인
5. 발송 UI + 상태 뱃지
6. **양식 확정 시**: placeholder → 실계약서 생성기 교체(§1 인터페이스 그대로)

## 8. 확정 필요(양식 오면)
- 계약서 문안(법무 검토본), 요청자 자동채움 필드 목록, anchor 텍스트 최종본,
  '계약완료'가 주문 파이프라인의 어느 게이트로 연결되는지.
